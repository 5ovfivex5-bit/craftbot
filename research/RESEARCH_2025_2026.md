## (a) Executive summary: top 5 recommended changes

Our bottleneck is COAL (~5%) from hard exploration, plus CPU budget (~3k agent-steps/s = ~10.8M steps/hour, ~5.6 min per 1M steps). Ranked by expected value per CPU hour:

### 1. Use the free-play recordings as goal-relabeled demonstrations, with a KL/residual tie to the frozen BC prior
- **What:** Pretrain the v6 policy by BC on the recorder v2 data (§9), relabeling every item the human obtained as a reached goal (rule-based hindsight, no LLM needed). Then fine-tune with PPO while keeping a KL-to-BC term that decays, or a residual head on a frozen BC base.
- **Backing:** Hindsight instruction relabeling of unsuccessful Craftax trajectories (arXiv 2506.20061, abstract only: claims better sample efficiency, no numbers seen). Posterior BC (arXiv 2512.16911, abstract only: "significantly improved RL finetuning", no numbers seen). Residual off-policy RL on a frozen BC base (arXiv 2509.19301, abstract only: sparse binary reward, real-robot). Advantage-conditioned training that mixes demos, on-policy data and interventions (pi*0.6 / RECAP, arXiv 2511.14759, opened: "more than doubles task throughput" and roughly halves failure rate on the hardest tasks; no exact figures in the text).
- **Benefit:** Directly targets coal. Dreamer 4 (arXiv 2509.24527, opened HTML) reports 0.7% diamond success even from 2.5K hours of offline contractor data, so offline data alone is not enough at diamond depth. Coal is far shallower, so the relevant claim is "human-coal trajectories give the policy coal behaviour to start from", which is testable only by us.
- **Cost:** Dev ~1-2 weeks (recorder v2 labels are specified in PROTOCOL §9; BC script exists in §8.4). CPU: BC on 1-3 h of data (about 0.16-0.5M sim-steps after 4-tick aggregation) is minutes; each 2M-step PPO run ~11 min.
- **Risk:** Human play is not sim-identical (MC physics vs our sim, obs mismatch). KL-to-BC can kill exploration. Our earlier 10-minute BC gave no gain (too small). Mitigation: decaying KL, 3 seeds, and measure coal rate, not return.

### 2. Coal-frontier archive with "opportunistic" sampling of hard-to-reach states (Go-Explore done as CODE-SHARP does it)
- **What:** Our trainer already has Go-Explore (disabled for K>1). Extend the archive to key on depth/y-level and on "has stone pickaxe" frontier cells, and sample restart states preferentially where success is low (CODE-SHARP's "opportunistic sampling"). Use `save_state/load_state` (already in §6.7).
- **Backing:** CODE-SHARP (arXiv 2602.10085, opened HTML). Its ablation on its Craftax-derived benchmark: full 50.55 vs 31.93 without opportunistic sampling, and 13.50 with no open-ended training, adaptive scaling or opportunistic sampling. Intelligent Go-Explore (arXiv 2405.15143, ICLR 2025, abstract) uses foundation-model "interestingness", which we cannot run on CPU cheaply; the archive idea transfers without an LLM.
- **Benefit:** Plausibly the largest coal gain for exploration, based on the CODE-SHARP ablation. Not measured on our sim.
- **Cost:** Low-medium: ~1 week. CPU: each 2M-step run ~11 min. K=1 only for now.
- **Risk:** Go-Explore restarts can overfit to the archive. Keep a fraction of normal resets.

### 3. Plasticity hygiene for the PPO trunk (SimBa-style normalization + dormant-unit reset), tested fairly this time
- **What:** Put the MLP/vector path and the post-GRU head in a SimBa-style block (running-stat input normalization, pre-LN residual MLP, final LayerNorm), and add a periodic reset of units with near-zero activation and gradient. This is NOT the "extra residual block bolted onto a trained net" that failed before; it is a from-scratch trunk change.
- **Backing:** SimBa (arXiv 2410.09754, ICLR 2025, opened HTML). Component ablation on DMC-Hard (1M steps, SAC): residuals about +50, LayerNorm about +150, full combination about +550 return points. Caveat: off-policy/SAC evidence. Reset evidence: ReSiN (arXiv 2505.01584, opened abstract: up to 168% bitrate in a video-streaming setting, not games, PPO not confirmed). P3O (Plastic PPO, ICML 2025, **unverified**, only a title snippet). Counter-evidence: "Rethinking Plasticity in Deep RL" (arXiv 2603.21173, opened abstract, single author): argues dormancy equals zero-gradient and that high dormancy can coincide with fast convergence, so resets are not automatically good.
- **Benefit:** Unknown; plausibly helps the 1.8M policy keep learning across the curriculum. Must be measured.
- **Cost:** Low: ~2-3 days. CPU: 1M-step ablation ~5.6 min per run; 3 seeds x 2 arms ~ 35 min.
- **Risk:** Mixed evidence on resets; RND/SPR/HL-Gauss already failed, so expect small effects.

### 4. Make the team message channel carry information (intention-style auxiliary loss + info bottleneck), keep IPPO-style parameter sharing
- **What:** Keep one shared policy with independent PPO per agent (current design). Add an auxiliary head that predicts the teammate's next goal or next 4-tick action from the message (a "plan" signal), and an information-bottleneck penalty on message entropy when messages are uninformative.
- **Backing:** Multi-Agent Craftax (arXiv 2511.04904, opened HTML/PDF): on Craftax-Coop, IPPO beat MAPPO in some settings and the authors argue popular MARL methods overfit to benchmarks; MAPPO is lowest final but fastest early in Coop; with fewer than 2% of episodes reaching the third of nine levels (Gnomish Mines) in the extended-run analysis. Communicating Plans, Not Percepts (arXiv 2508.02912, opened abstract, NeurIPS 2025 SEA workshop): an engineered "intention" message beats learned direct communication, with qualitative claims only. Karten et al. (arXiv 2302.14276, 2023, snippet) on information-bottleneck messages.
- **Benefit:** Team score likely depends more on chests/give/sharing than on messages; the coal goal is solo. Expected benefit modest; not a priority for coal.
- **Cost:** Low-medium: ~1 week. CPU: each 2M-step, K=4 run needs 4x agent-steps per world step; budget accordingly.
- **Risk:** Message head may remain silent (entropy collapse). Measure msg_entropy and msg_rate (already logged).

### 5. Test a state-space or linear-recurrent memory only for throughput, keep GRU as default
- **What:** Benchmark LRU / Mamba-2 / S5-style memory as a drop-in for the GRU in the same PPO trainer, measuring steps/s on the Steam Deck CPU first. Adopt only if throughput rises and coal rate holds.
- **Backing:** RLBenchNet (arXiv 2505.15040, opened abstract/page): Mamba models 4.5x throughput vs LSTM and 3.9x vs GRU with "comparable performance"; Mamba-2 uses 8x less memory than Transformer-XL on the hardest memory tasks. Not a PPO study (PPO not mentioned on the page). Counter-evidence: Zero-shot RL under partial observability (arXiv 2506.15446, opened abstract only): memory-based methods help, and the performance numbers for GRU vs transformer vs S4d were not in the abstract, so I cannot state them. Older POPGym / Memory Gym results (snippets) favour GRU.
- **Benefit:** Only via more steps per hour (a 1.5x throughput gain would be ~16M steps per hour instead of 10.8M). Accuracy gain unknown.
- **Cost:** Low for a benchmark (~1 day); medium to adopt.
- **Risk:** Earlier transformer/SSM memory results were worse in several settings.

### What we should NOT do (given evidence)
- Dreamer 4 / EMERALD / TWM-style world models: GPU-scale (Dreamer 4 is 2B params and 2.5K hours of data). Not feasible on Steam Deck. TWM on Craftax-classic (arXiv 2502.01591, opened abstract) reports 69.66% at 1M steps vs DreamerV3 53.2% and human 65.0%, but it is a GPU-trained transformer world model; we could copy the "Dyna with warmup" idea only later.
- LLM-in-the-loop exploration (SCALAR, IGE, SGRL, OMNI-style): SCALAR (arXiv 2603.09036, opened abstract) reports 88.2% diamond collection on Craftax, 1.9x best baseline, 9.1% Gnomish Mines, but requires an LLM and RL per skill. Not feasible offline on CPU, and the numbers are self-reported.
- Video-only pretraining (VPT/D2E/Amplify): we already record exact keys and events, so we do not need an inverse-dynamics model. IDM tricks are only useful if we want to learn from unlabeled YouTube video.

## (c) Experiment plan for the top 3

Common setup: sim `craftsim` v6, agents=1 for E1 and E3 (Go-Explore needs K=1), agents=4 for E2 only if time allows. Baseline = current v6 checkpoint. Measure at 2M agent-steps per run: coal rate (primary), stone_pickaxe and furnace rates (must not regress), and a second-seed check. Seeds: 3 per arm (`--seed`). CPU time at ~3k agent-steps/s: 1M ~5.6 min, 2M ~11 min, 10M ~56 min.

### E1. Free-play relabel + BC warm start + decaying KL-to-BC (Rec. 1)
- **Files:** `pretrain/recordings.py` (aggregate recorder v2 to 4-tick steps; add rule-based hindsight labels: for each item the human obtained at time t, store "goal reached = item" for the preceding window); `pretrain/bc.py` (BC with goal one-hot = relabeled goal, 64-step GRU chunks); `trainer/` PPO loss: add `--bc-kl coef` with linear decay to 0 over the first 1M steps, reference = the BC model's action distribution.
- **Data:** 1 h and 3 h recorder sessions (or 3 h of recorded play simulated with `pretrain/fake_recording.py` for the pipeline test only).
- **Arms:** (A) baseline; (B) BC warm-start, no KL; (C) BC warm-start + KL decay; (D) optional: advantage-conditioned variant (RECAP-style indicator from value).
- **Success criteria:** coal >= 20% at 2M steps (baseline ~5%), averaged over 3 seeds, with stone_pickaxe >= 90% and furnace >= 80%. Failure modes to log: entropy collapse (`ent`), KL magnitude.
- **CPU:** BC ~minutes on 1-3 h data; each PPO arm 2M steps ~11 min; 4 arms x 3 seeds ~2.2 h.
- **Kill rule:** if arm C is not better than arm A at 2M, stop before any scale-up.

### E2. SimBa-style trunk + dormant-unit reset for PPO (Rec. 3)
- **Files:** `trainer/model.py` (replace the post-GRU MLP and vec encoder with RSNorm + pre-LN residual block x2 + final LN; keep CNN); `trainer/` add `--reset-every N --reset-frac f` that re-initialises units with activation ~0 over the last N updates (reset incoming weights, zero outgoing); log dormant fraction.
- **Arms:** (A) current model; (B) SimBa trunk only; (C) SimBa + reset (reset only the trunk units, not the GRU).
- **Success criteria:** coal and iron_pickaxe-stage metrics not worse than baseline, and dormant fraction measurably lower; any improvement must hold on 3 seeds. Also must not break the `--warm-start` path (rebuild warm-start mapping, or start new runs only).
- **CPU:** 1M steps per run ~5.6 min; 3 arms x 3 seeds x 1M = ~50 min; extend winners to 4M (~22 min each).
- **Kill rule:** if B and C are within seed noise at 1M, revert to current model (keeps the 1.8M-param design).

### E3. Coal-frontier archive with opportunistic restarts and prerequisite-gated reward (Rec. 2, Rec. 3 in CODE-SHARP sense)
- **Files:** trainer Go-Explore code (currently disabled for K>1; use K=1); archive keys = (y-level bucket, has_stone_pickaxe, has_furnace); restart sampling weight proportional to (1 - recent success on that cell) (opportunistic sampling); use `CraftSim.save_state/load_state` (PROTOCOL §6.7 blob limit 2 MB). Optional: coal reward active only when stone_pickaxe is held (prerequisite routing), so the coal reward is not diluted.
- **Arms:** (A) baseline; (B) archive with uniform restarts; (C) archive + opportunistic weighting; (D) C + prerequisite-gated coal reward.
- **Success criteria:** coal >= 20% at 2M steps for C or D, 3 seeds, with no regression in early goals (>= 95%).
- **CPU:** each 2M run ~11 min; 4 arms x 3 seeds = 2.2 h. Save-state blob size must be checked per archive cell.
- **Kill rule:** if C is not better than B by a clear margin, stop; keep only the archive as a diagnostic.

Rec. 4 (team messages) and Rec. 5 (SSM memory) are not in this first plan: Rec. 4 is low priority for the solo coal goal, and Rec. 5 needs a steps/s benchmark first (~1 day, measure with the existing trainer on the Steam Deck).
